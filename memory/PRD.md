# WeAre Creators — PRD

## Original problem statement
Two-sided marketplace web app for Bengaluru connecting food & lifestyle content creators
with restaurants, cafés, and lifestyle brands for paid collaboration campaigns. Three user
roles: CREATOR, BRAND, ADMIN. Dark premium theme, burnt-orange accent, elegant serif +
clean sans, mobile-first. Foundation only for first build: auth + DB + role-based access +
placeholder home + login/signup. GitHub sync via Emergent UI.

## Stack (confirmed)
- Backend: FastAPI + Motor (MongoDB), JWT email/password auth, bcrypt
- Frontend: React 19 + Tailwind + Shadcn UI, framer-motion, sonner
- DB: MongoDB (managed)
- Fonts: Instrument Serif (headings) + DM Sans (body)
- Accent: Burnt Orange `#F05D14`
- Background: near-black tinted grey `hsl(20 8% 4%)`

## User personas
- Creator: Bengaluru food/lifestyle content creator applying to paid briefs.
- Brand: Restaurant/café/lifestyle brand posting briefs.
- Admin: WeAre Monk internal team curating both sides.

## Core requirements (static)
- Role-based access: creator | brand | admin
- Creators & brands: WhatsApp OTP login/signup (AiSensy delivery). Admin: email + password.
- Mobile-first, premium dark editorial UI
- All backend routes prefixed with `/api`

## Implemented (v0 — Feb 2026)
- JWT auth: register/login/logout/me/refresh, httpOnly cookies, bcrypt hashing
- Admin auto-seed from env on startup
- MongoDB unique indexes: partial-unique on `users.email` + `users.phone` (string-typed only)
- Role guard dependency (`require_roles`) + sample `/api/admin/ping`
- Frontend: Landing page, WhatsApp OTP Login (`/login`), Signup with role picker (`/signup`), Admin email login (`/admin/login`), role-aware Dashboard shell, ProtectedRoute, Navbar, AuthContext
- Design system: Instrument Serif + DM Sans, burnt-orange accent, dark tinted-grey base

## Implemented (v1.1 — WhatsApp OTP Auth, Feb 2026)
- New `otp_codes` collection (TTL 5 min, bcrypt-hashed codes, attempt counter)
- `POST /api/auth/otp/request` — 30s per-phone cooldown, 5/hour per-phone limit, purpose=login|signup
- `POST /api/auth/otp/verify` — 5-wrong-attempt lockout, issues JWT cookies on success
- AiSensy WhatsApp delivery with simulation mode when creds missing (logs OTP)
- `/auth/login` now admin-only (role=admin gate); creators/brands must use OTP
- Startup migration drops legacy single-field `email_1`/`phone_1` indexes before creating partial-unique variants

## Data model (v1 — Feb 2026)
Collections + indexes provisioned on startup. All linking IDs are `ObjectId`.

- `users` — id, email(unique), name, role(creator|brand_manager|admin|campaign_manager; `brand` is the pre-rename spelling and still accepted), phone?, status(pending|active|suspended), password_hash, brand_id? (brand managers only — the brand they act for; equal to their own _id for a self-registered brand), manager_name?, manager_designation?, manager_email? (the named contact captured at registration), created_at. Indexes: `email` unique, `role`, `status`, **partial-unique `brand_id` where role=brand_manager** (`one_manager_per_brand`) — one login per brand, enforced by the database rather than by everybody remembering.
- `creator_profiles` (1:1 users where role=creator) — user_id(unique), name, instagram_handle?, instagram_profile_url?, youtube_url?, profile_image_url?, email?, city?, address (the neighbourhood a brand filters on), full_address? (where post actually goes), niches[] (what they cover for a brand: cafe, brunch), genres[] (what they make: food, travel — a brand searches on one and briefs on the other), platforms[] (instagram|youtube, a closed list so the directory stays searchable), base_rate?, follower_count? (self-reported), verification_status(pending|verified|rejected), pending_review, submitted_for_review_at? (set only by the creator submitting; the vetting queue's key), onboarding_nudge_sent_at? (set once, ever, by the 3-day chase), payout_upi?, payout_account_name?, pan?, gstin?. The stub created at signup holds a name and nothing else. niches and genres are stored lower-cased, since campaign suggestions match on them. Indexes: `user_id` unique, `verification_status`, `(verification_status, submitted_for_review_at)`, `(onboarding_nudge_sent_at, created_at)`, `niches`.
- `brand_profiles` (1:1 users where role=brand) — user_id(unique), business_name, legal_entity_name?, gst_number? (optional; normalised and format-checked when given), business_type(sole_proprietorship|partnership|llp|private_limited|public_limited|trust|society|other)?, category(fnb|hospitality|retail|lifestyle)?, registered_address?, website?, instagram_handle?, facebook_url?, linkedin_url?, contact_person_name?, contact_person_designation?, contact_email? (the work email), contact_phone?, areas[], verified, verification_state(unsubmitted|pending_verification|verified|rejected), submitted_for_verification_at?, verified_at?, verification_reason? (why we refused), rejected_at?. `verified` stays the boolean everything gates on; `verification_state` says *why* it is false. Unverified brands may draft campaigns and edit their own profile, and nothing else that reaches a creator. Indexes: `user_id` unique, `verified`, `category`, `(verified, verification_state, submitted_for_verification_at)`.
- `brand_documents` (many per brand) — brand_id → users._id, doc_type(gst_certificate|business_registration|fssai_licence|shop_establishment_licence), stored_name (ours, random, the only name on disk), original_name (a label, never a path), mime, size, status(submitted|accepted|rejected), review_note?, created_at, updated_at. Files live in `PRIVATE_UPLOAD_DIR` — deliberately not the `StaticFiles`-mounted `UPLOAD_DIR`, since these carry registered addresses and directors' names. No route returns a path or a URL; the bytes come out only through the audited admin fetch. Capped at 12 per brand. Indexes: `(brand_id, created_at desc)`.
- `campaigns` — brand_id → users._id, title, brief, deliverables, budget_per_creator, category?, area?, creators_needed, start_date?, end_date?, campaign_type(launch|group_event|personal_table), event_date? (launch/group_event only), venue_address?, venue_instructions?, on_site_contact?, manager_id? → users._id, manager_name?, manager_phone?, manager_email?, status(draft|pending_review|upcoming|open|in_progress|paused|completed|closed), submitted_for_review_at?, reviewed_at?, reviewed_by?, review_reason?, paused_at?, paused_from_status?, pause_reason?, closed_at?, closed_by_admin?. The type decides the dates: launch/group_event carry event_date and no window; personal_table carries start_date+end_date and no event_date — enforced in PostCampaignPayload. Manager fields are a snapshot taken at assignment. A brand may only set draft or pending_review; only an admin approval reaches open/upcoming. Indexes: `brand_id`, `status`, `(status, created_at desc)`, `(area, category)`.
- `collaborations` — campaign_id → campaigns._id, creator_id → users._id, pitch?, quoted_rate?, agreed_amount?, content_url?, preferred_time? (the hour a creator named inside a personal-table window; the window still carries the capacity), slot_cancelled_at?, slot_cancel_reason?, state(applied|verified|accepted|commercial_agreed|slot_booked|attended|content_submitted|content_approved|in_payment|closed) plus terminal exits (declined|cancelled), active, slot_id? → campaign_slots._id, checked_in_at?, no_show_reported?, no_show_note? (raised by the manager, actioned by an admin), rescheduled_at?, scheduled_at?, agreed_at?, exit_reason?, cancellation_type(creator_no_show|brand_cancelled|admin_cancelled)?, cancelled_from_state?, agreed_amount_at_cancellation?, settlement_review_needed?, reverted_from?, revert_reason?. Indexes: `campaign_id`, `creator_id`, **partial-unique `(campaign_id, creator_id)` where active=true** so a declined creator may re-apply, `state`.
- `campaign_invitations` — campaign_id → campaigns._id, creator_id → users._id, brand_id, invited_by → users._id, note?, state(sent|send_failed), delivered_on_whatsapp, whatsapp_mode?, error?. Indexes: **unique `(campaign_id, creator_id)`** so nobody is invited twice, `(creator_id, created_at desc)`.
- `campaign_slots` — campaign_id → campaigns._id, starts_at, ends_at? (required for personal_table windows), capacity, booked_count, created_by → users._id. Editable by the assigned manager: capacity never below booked_count, and moving the time re-stamps the collaborations on it. Booking increments booked_count under a `$expr` capacity check, so the last place resolves inside the database. Indexes: `(campaign_id, starts_at)`.
- `payments` (1:1 collaborations) — collaboration_id(unique), agreed_amount, platform_fee, creator_payout, state(pending|paid|cancelled|refunded), paid_at?, payment_reference?, refunded_at?, refund_reason?, refund_reference?, brand_invoice_state(pending|sent|settled|void), brand_refund_due?. `cancelled` is a payout that never happened; `refunded` is one that did and came back. Indexes: `collaboration_id` unique, `state`.
- `instagram_connections` (1:1 with creators who connected) — user_id(unique), ig_user_id, username?, account_type (BUSINESS|MEDIA_CREATOR), access_token (Fernet ciphertext over INSTAGRAM_TOKEN_KEY; never returned by any route), token_expires_at, scopes[], status(connected|stale), stale_reason?, stats{followers_count, media_count, reach, engagement}, stats_fetched_at?, connected_at, last_refreshed_at. Kept out of `creator_profiles` so no profile serializer can leak the token. Indexes: `user_id` unique, `(status, token_expires_at)`, `(status, stats_fetched_at)`.
- `instagram_oauth_states` — state(unique), user_id, expires_at. Single-use, consumed with `find_one_and_delete`, TTL-expired by Mongo.
- `collaboration_notes` (many per collaboration) — collaboration_id → collaborations._id, campaign_id, brand_id, author_id → users._id, author_name, author_role (stored, not joined: "the brand said" and "WeAre said" is most of what a thread is for, and a manager who later becomes an admin must not rewrite what they were), body, created_at. Append-only — no edit route, no delete route. Read by the brand manager on their own campaigns, by admins, and by the assigned campaign manager; never by the creator. Indexes: `(collaboration_id, created_at)`, `(campaign_id, created_at)`.
- `audit_log` — actor_id → users._id, actor_role, actor_name, action (`<subject>.<verb>`, e.g. `payment.refund`), subject_type, subject_id, brand_id?, campaign_id? (the context the subject alone doesn't carry — a brand manager's actions land on collaborations, payments and slots as often as on the campaign), before, after, note, created_at. Written by every admin and brand mutation. Indexes: `created_at desc`, `(subject_type, subject_id)`, `(actor_id, created_at desc)`, `(action, created_at desc)`, sparse `(brand_id, created_at desc)`, sparse `(campaign_id, created_at desc)`.

On signup, a stub row is auto-created in `creator_profiles` or `brand_profiles` so downstream flows can rely on the profile existing.

## Instagram stats (Aug 2026)
- **"Instagram API with Instagram Login"**, not the Facebook-Login flow — the latter requires every creator to link a Facebook Page, which most of ours don't have. `graph.facebook.com` appears nowhere in the codebase and a unit test keeps it that way. This replaces the removed Apify scraper, which breached Instagram's terms.
- Scopes: `instagram_business_basic` and `instagram_business_manage_insights`. Read-only; nothing can post, message or change anything on a creator's account.
- `POST /api/creator/instagram/connect` issues a single-use, server-stored, creator-bound state and the authorize URL. `POST /api/creator/instagram/callback` exchanges code → short-lived → long-lived token (`ig_exchange_token`), takes a first reading, and refuses a non-Professional account with `{"code": "not_professional"}` plus the steps to switch. `DELETE /api/creator/instagram` disconnects; `POST /api/creator/instagram/refresh` re-reads within the cache window.
- Tokens are Fernet-encrypted at rest and live in `instagram_connections`. `_encrypt_token` raises rather than falling back to plaintext when no key is set; an undecryptable token (rotated key) reads as absent and the connection goes stale, which is recoverable.
- `refresh_instagram_tokens` renews the 60-day token `INSTAGRAM_REFRESH_WINDOW_DAYS` (7) before expiry. Revoked/expired (`_is_revoked`) → `status: stale`, token dropped, creator notified to reconnect; a transient Graph error is deferred instead. `refresh_instagram_stats` pulls followers, media count, reach and total interactions for connections stale beyond `INSTAGRAM_STATS_TTL_HOURS` (12). Insights are best-effort so a quiet account still gets its follower count. Both run from a startup loop (`INSTAGRAM_JOB_INTERVAL_SECONDS`, 0 disables) and from `POST /api/admin/jobs/instagram` (audited as `job.instagram_refresh`).
- Never fetched on a dashboard load: the limit is 200 calls per user per hour and a reading costs three.
- While connected the live figure is mirrored onto `creator_profiles.follower_count` with `follower_count_source: "instagram_verified"`, so the brand directory can sort and filter without a join. `follower_count_self_reported` is preserved and restored on disconnect, and a typed number can't overwrite a verified one. `_follower_provenance` ships the source with the number on the creator profile, the dashboard, the admin row and the brand directory.
- Absent credentials is a supported state — connect routes 503 with an explanation, jobs no-op, the UI renders a visibly inert button saying the app is in review, and counts stay self-reported.
- Frontend: `components/creator/InstagramConnect.jsx` (card, states, scope disclosure, professional-account guidance) and `pages/InstagramCallback.jsx` at `/onboarding/creator/instagram`, which must match `INSTAGRAM_REDIRECT_URI`.

## Brand verification (Aug 2026)
- The problem: anyone could sign up, type a restaurant's name into `business_name` and be treated as that restaurant. Verification was a bare admin toggle with nothing behind it to check.
- `PUT /api/brand/profile` is a partial save (`model_fields_set`) carrying the business identity — legal entity, business type, registered address, optional GST number, website and official socials — plus the person asking: contact name, designation, work email, phone. Editing it stays open to an unverified or rejected brand; a brand that can't fix itself can't be verified.
- `POST /api/brand/verification/documents` — one proof-of-business file per call: GST certificate, business registration, FSSAI licence or shop & establishment licence. Any one is enough (a café has a shop licence and no GST; a company has an incorporation certificate and no FSSAI). Several are allowed, up to 12, and nothing is deleted on upload, so a clearer scan after a rejection doesn't cost the rest. `DELETE .../documents/{id}` removes one, and is refused once the brand is verified — the file is the evidence for a decision already made. Magic-byte sniffed exactly like the creator profile image (`sniff_document_type` = the image signatures plus `%PDF-`), same size ceiling.
- **Storage.** `PRIVATE_UPLOAD_DIR` (default `backend/private_uploads`), deliberately *not* `UPLOAD_DIR`: that one is mounted as `StaticFiles` and anything in it is fetchable by anyone who guesses the name. The stored name is server-generated and random; the uploader's filename is kept only as a label and never touches the disk. `_serialize_brand_document` returns no path and no URL, and the only way to the bytes is `GET /api/admin/brands/{user_id}/documents/{id}` — admin-only, filtered on both ids, `Cache-Control: no-store`, audited on every read. `_private_upload_path` resolves and `relative_to`-checks, so a crafted stored name can't walk out of the directory.
- `POST /api/brand/verification/submit` — allowed only with all eight required fields (`_BRAND_REQUIRED_FIELDS`) and at least one document; 409s naming exactly what's absent. Sets `verification_state: pending_verification` and stamps `submitted_for_verification_at`, which is what the queue sorts on.
- `GET /api/admin/brands/pending` is now `verified: false` **and** `verification_state` in `pending_verification | rejected` — a bare signup is no longer a queue item with nothing to decide on. Each row carries the business details, the contact person, and the documents (one query for all of them, not one per brand), and flags `contact_email_is_free_domain`: a Gmail address is not a rejection — plenty of real small businesses run on one — but the reviewer should be told. `POST .../verify` and `POST .../reject` (reason required) decide and WhatsApp the brand either way; the rejection quotes the reason so they know what to fix. `POST .../documents/{id}/review` marks a single document accepted or rejected with a note.
- **The gate** is `_verified_brand_or_403`, applied to every endpoint that reaches a creator: publish, create campaign, the creator directory and its filters, the applicant list, accept, decline, approve content, request changes. Drafting and profile editing stay open. `_why_brand_is_blocked` answers with the state's own next step — still-building names the outstanding fields, waiting-on-us gives the 48-hour expectation, rejected quotes the reason.
- **Ownership is resolved before verification** on every gated endpoint that has an owner. The other order turns another brand's campaign from a 404 into a 403, which tells a probing brand which ids exist; a parametrised unit test pins the order.
- Startup backfills `verification_state` on rows written before the field: verified → `verified`, a stored refusal reason → `rejected`, everything else → `pending_verification`, so nobody already waiting in the old queue silently drops out of the new one.

## The brand manager (Aug 2026)
- The problem: a brand account was a nameless login. Campaigns had no contact on them until an admin assigned a WeAre manager, an audit line said "the brand" rather than a person, and a brand that wanted to pause its own brief had to email us.
- **One named person per brand, and it is the brand's only login.** Registration captures full name, designation, WhatsApp number (which *is* the login) and work email; the same three land on `brand_profiles.contact_person_*`, which is exactly what verification asks for, so nothing is typed twice. The role is `brand_manager`; `BRAND_ROLES = ("brand", "brand_manager")` keeps pre-rename accounts working and startup migrates real ones over (demo feed rows, which have no phone and nobody signs into, are left alone). A second manager is refused by a partial-unique index, not by a rule somebody has to remember.
- `_brand_scope(user)` is how every brand-scoped query finds its brand — never `user["_id"]`, which is correct only while the login and the brand are the same row. A unit test fails any brand endpoint that reaches for the raw login id.
- **Campaigns default their manager to the brand's own person** (`_brand_manager_contact`), so a brief has a named contact from the moment it is drafted rather than from whenever an admin gets to it. An admin can still reassign to a WeAre manager.
- That default means `_managed_campaign_or_404` would admit a brand manager to the `/manager` router on ownership alone. The role guard is what keeps them out — and out of the daysheet CSV, which carries creators' phone numbers by design. A unit test asserts every `/manager` route is `require_roles("campaign_manager", "admin")`.
- On their own campaigns the brand manager can pause, resume, close, edit while draft, accept and decline, invite (verified brands only), record the fee agreed offline, approve content or request changes, mark attendance, and read a phone-free roster. **Going live stays with admin review.** Pause, resume, invite and check-in share one implementation with the admin routes so the two cannot diverge.
- Notifications: applications, slot booked/cancelled/rescheduled, content submitted, a creator cancelling or no-showing, WeAre verifying or rejecting the brand or a campaign, and WeAre editing their campaign (the message names the fields). `notify_brand_manager` skips the actor's own action; `_tell_brand_manager_unless_managed` skips the message when the campaign manager *is* the brand manager and has already been told, because two WhatsApps for one booking is how a channel stops being read.
- Every action audits with `brand_id` and `campaign_id` attached (`_campaign_audit_context`), and `GET /api/admin/audit` filters on both.

## Creator data minimisation (Aug 2026)
- `_brand_visible_creator` is the single projection behind every brand-facing surface — directory, applicant board, suggestions panel, notes header. An allow-list, not a strip-list: name, photo, Instagram and YouTube handles with public stats, follower count and its provenance, engagement rate, city, niches, genres, platforms, base rate, verification status.
- **No phone number, WhatsApp number, email or full address reaches a brand, at any collaboration state.** This is a change: the applicant board revealed an email and a phone from `accepted` onwards, so accepting an application handed over a contact the creator never offered. The invite flow reads the number server-side and never returns it; on the day a brand reaches creators through the platform.
- `BRAND_FORBIDDEN_CREATOR_FIELDS` is asserted two ways: a unit test walks every brand response shape for both the forbidden keys and the actual values, and an integration test does the same against live HTTP responses.
- The WeAre manager's roster and daysheet still carry phone numbers — that is the job of the person standing at the door — and stay behind the staff role. `_roster_rows(..., reveal_contact=False)` builds the brand's copy with the key absent rather than null, so a brand response has no creator-contact shape at all.

## Work notes on a collaboration (Aug 2026)
- `POST`/`GET /api/collaborations/{id}/notes`. Offline negotiation is the model, not a gap in it, which means the reasoning behind a fee lives in somebody's head until they leave. This is where it goes instead.
- Author, role at the time of writing, body and timestamp. The agreed amount and the quoted rate are returned above the thread, because reading one without the other is what made a fee look arbitrary a month later. A note supplied with `POST /brand/collaborations/{id}/agreed-amount` lands in the thread too.
- Readable by the brand manager on their own campaigns, by admins, and by the assigned campaign manager. Creators never see them and the route does not accept the role. Refusals are 404s: whether a private thread exists on somebody else's collaboration is itself not answered.
- Append-only. No edit route and no delete route — a record of a negotiation that can be quietly rewritten is not a record. Corrections are another note. Every note is audited.

## Suggested creators (Aug 2026)
- `GET /api/brand/campaigns/{id}/suggested-creators` — the verified roster ranked for one brief, so a brand can go and ask rather than wait for whoever happens to be browsing. Available to admins on any campaign.
- The score is `score_creator_for_campaign`: one pure function, no database access, no hidden term. `CREATOR_MATCH_WEIGHTS` sums to 100 (niche 30, genre 15, city 20, reach fit 15, engagement 10, delivery 10) and is the only place to tune it — in code, not in the database, because a ranking that silently differs between environments is one nobody can debug. Every response carries the per-component breakdown and the weights used.
- Reach fit is judged against the budget tier (`CREATOR_REACH_TIERS`): both directions are a mismatch, since a 500k creator will not turn up for ₹2,000 and a 900-follower account is not what ₹50,000 is buying. `CAMPAIGN_CATEGORY_SYNONYMS` bridges the category enum to the words creators use about themselves — nobody writes "fnb".
- **Unmeasured signals score at the midpoint, never zero**, and are named in `unknown_signals`. A creator with no connected Instagram has an unknown engagement rate, not a bad one; scoring unknowns at zero would bury everyone who has never worked here, which at the start is everyone.
- Each row carries a one-line reason ("Matches Fashion and Beauty, based in Indiranagar, 24k followers"). Anyone who already applied or was invited is excluded. Filters for niche, city and follower range; paginated; ordering broken all the way down to the name so two identical requests paginate identically.
- Frontend: `components/brand/SuggestedCreators.jsx` on the campaign applicants page — match reason on every card, the breakdown one click away, and an invite button that reuses the invite endpoint. `components/brand/WorkNotes.jsx` renders the thread on each application, replacing the "contact unlocked" panel that used to show a creator's phone number and email.

## Creator onboarding (Aug 2026)
- Signup (`/auth/otp/request`, `/auth/otp/verify`) takes a name, a WhatsApp number, a role and terms consent. Nothing else — the creator profile stub it writes is deliberately empty rather than half-guessed.
- `PUT /api/creator/profile` is a partial save: only the keys present in the body are written, so the builder can be filled in across sessions without a later step blanking an earlier one. Every field is optional; an omitted key means "leave it alone" and an explicit null means "clear it". `_clean_payout_fields(..., only=sent)` applies the same rule to the payout identity.
- `GET /api/creator/profile` returns `profile_completeness` alongside the profile, so the builder's submit button and the server's gate share one definition of "done".
- `POST /api/creator/profile/submit-for-review` — the only thing that puts a creator in front of an admin. 409s below 100% naming the missing fields, 409s for an already-verified creator, clears any previous rejection reason, audits (`creator.submit_for_review`) and notifies. Sets `submitted_for_review_at`, which `/admin/creators/pending` and every awaiting-count now filter on via `_AWAITING_REVIEW_QUERY`; startup backfills it from the old "pending + has a handle" heuristic so nobody already waiting drops out of the queue.
- Completeness asks for a channel per platform the creator selected (`_PLATFORM_COMPLETENESS_FIELDS`), never across the board — an Instagram-only creator who could never reach 100% could never submit at all. Payout details are outside it on purpose.
- `POST /api/campaigns/{id}/apply` 403s anyone not verified, with a message that distinguishes still-building (naming the outstanding fields), waiting-on-us, and rejected (quoting the reason). Browsing and reading a brief stay open to everyone.
- `nudge_stale_creator_profiles` — one WhatsApp chase, ever, to creators who signed up `PROFILE_NUDGE_AFTER_DAYS` (3) ago with an unfinished, unsubmitted profile. The `onboarding_nudge_sent_at` stamp is claimed before the send under a filter that only matches while it's absent, so a race sends once and a failed send is still used up. A finished-but-unsubmitted profile is skipped — that is a different message. Driven by a startup asyncio loop (`PROFILE_NUDGE_INTERVAL_SECONDS`, 0 disables) and by `POST /api/admin/jobs/creator-nudges` (audited as `job.creator_nudges`).
- Frontend: `pages/CreatorOnboarding.jsx` is the builder — progress ring, named missing fields, per-platform channel fields that appear on selection, "Save progress" always live and "Submit for review" only at 100%. `pages/Dashboard.jsx` steers a creator with a 0% profile to it once per browser session, and carries a banner for the finished-but-unsent case.

## Creator experience (Aug 2026)
- `GET /api/creator/campaigns/{id}/slots` — the schedule as the creator sees it, gated on actually being on the campaign (accepted onwards): an applicant the brand has not taken sees a 404, because a slot list names dates, capacity and a venue's rhythm. Full slots come back marked rather than hidden. Carries `can_book`, `picks_own_time` (personal_table), the creator's own booking, the cancellation cutoff, and their invitation where one exists — an invitation is surfaced, never required, since applying off the open list puts you on the campaign just as much.
- `POST /api/creator/collaborations/{id}/book-slot` — takes a place, moving `commercial_agreed → slot_booked`. Shares one atomic claim (`_claim_slot`) with the campaigns-router booking route, so the conditional `booked_count` increment exists once. On personal_table the body must name a `preferred_time` inside the window; on launch/group_event a supplied time is refused, because everyone arrives together.
- `POST /api/creator/collaborations/{id}/cancel-slot` — hands the place back up to `SLOT_CANCEL_CUTOFF_HOURS` (24h) before it. Returns to `commercial_agreed` rather than ending the collaboration: still on the campaign, just not on that slot. The collaboration is written before the seat is released, so the place is never on sale while the creator still holds it. Audited, and the manager is notified.
- `GET /api/creator/dashboard` — extended with `earnings` (lifetime_earned, pending_earnings, campaigns_completed — both figures net of the platform fee, with refunded and cancelled payouts counted nowhere), `collaborations` grouped active/completed/applied/declined (exhaustive, so nothing drops out of a creator's own record; `content_approved` and `in_payment` sit in active because the work is done but the money isn't in), `profile_completeness` (equal-weighted percentage plus the fields still missing), and `suggested_campaigns` (live campaigns matching their niches, genres or neighbourhood that they aren't already on, each with the reason it matched). Active rows carry the campaign, the manager's name and phone, the venue address and instructions, the booked slot time, and the one next action required from the creator. The pre-existing keys are unchanged.

- Creator home (`frontend/src/pages/Dashboard.jsx` + `components/creator/`) — one scrolling page off the single dashboard call: hero with the lifetime figure counting up, a completeness ring that disappears at 100%, active collaborations each carrying a six-stage lifecycle tracker (Applied -> Approved -> Slot booked -> Attended -> Content sent -> Paid), the manager as a `tel:` link, the venue, the booked time and the stage's own action button, a two-step slot picker dialog (windows/times, then a review), suggested campaigns with their match reason, applications split into waiting and went-another-way, and earnings by campaign. Motion is entrance-only and every piece of it checks `useReducedMotion`.

## Admin console aggregation (Aug 2026)
- `GET /api/admin/dashboard` — one call for the landing view: campaign counts by status (zero-filled, with `live` aliasing `open`), the five review queues plus a headline that is their sum, totals (GMV, paid out, active creators, active brands), and a per-campaign summary with applied/approved/rejected/completed counts. Optional `campaign_id` scopes every number to one brief; the platform-wide vetting queues read zero when scoped, since they are not that campaign's business. Four aggregations (`$facet`/`$group`), a fixed number of round trips whatever the data looks like.
